# Legacy approval and ID-rule audit (SQL Server)

`ops/sql/legacy-approval-id-rule-audit.mssql.sql` is a read-only preflight for data created before shared approvals (V219) and period-aware ID issuance (V218). It does not insert approvals, rewrite rules, or change business state.

Run it with a read-only database principal against a restored production backup, or during a write-quiesced window after V218/V219 are applied. Capture the three result sets in a restricted location: they contain document IDs and actor IDs. Do not check production output or credentials into Git. Separate `SELECT` statements are not an atomic snapshot under ordinary read committed isolation; rerun after stopping writers before using a report for a transition decision.

1. RMS recipes: `SOURCE_CHAIN_COMPLETE` means the source approval history has the expected ordered Draft → WaitApproval → Approved1 → Approved (→ Released) chain, original actors, keys, and hashes. It is a candidate for a separately reviewed migration, **not permission to manufacture COM history**. All other findings require investigation; especially `SELF_APPROVAL_CONFLICT`, `SHARED_KEY_COLLISION`, `STATE_MISMATCH`, and `SOURCE_CHAIN_INCOMPLETE`. `Rejected` is always manual review because older code permitted transitions the shared approval process now rejects. A returned row with an existing COM approval is a reconciliation problem, not a backfill candidate.
2. QMS 4M changes: `REQUEST_TIME_UNPROVEN` means a requester is present but the old table has no distinct request timestamp or append-only request event. `CREATED_AT` is shown only as evidence for review; it is **not** assumed to be `REQUESTED_AT`. Approved rows with missing actor/time and rejected rows without a decision event remain exceptions. None of the QMS missing-COM findings authorizes automatic approval reconstruction.
3. ID rules: findings identify unsupported cycles, invalid/exhausted counters, missing or misplaced `{period}` templates, and legacy periodic issuance with unknown `SEQ_PERIOD`. Do not simply add `{period}` or reset `CURRENT_SEQ`: first inventory all identifiers already issued by every consumer of the rule and prove the new format/period cannot collide. Record the chosen effective period and cutover in an approved, auditable migration.

Before any write-capable follow-up, reconcile each row with source history, user identity, timestamp provenance, existing COM records and global idempotency keys on a backup. Design the follow-up as an atomic, restartable transition with a preserved source-to-target evidence mapping and a rollback rehearsal. Keep affected approval actions and ID issuance disabled or fail-closed until that transition is verified. This audit alone does not certify that a production database is safe to migrate.
